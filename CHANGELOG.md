# Changelog

All notable changes to this project are documented in this file.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Changed

- **BREAKING: a unit's constant energy intensity is now metered on its product flow, not its inlet.** `OpsBlockData.add_constant_intensity_relation` keys `power_electrical[t]` to the flow the unit *delivers*, so `energy_intensity` reads as energy per unit of output. `ConstantEnergyIntensityModel` and `Pump` move to the outlet flow (numerically unchanged — the SISO pass-through ties it to the inlet), `Exchanger` to `flow_out_a`, and **`ReverseOsmosis` to `permeate`**, which does change value: its 3.0 kWh/m^3 default is now the specific energy consumption per m^3 of permeate that the desalination industry quotes, so at a recovery below one the same number means a smaller absolute draw than the previous feed-based reading. The `Pump` hydraulic relation is untouched — it is a physical power law, not an energy intensity. The basis is recorded per `PowerKind` on the new `IORegistry.intensity_basis`, and `flexparameterize.apply_to_model` regresses against exactly that stream (falling back to a unit's single non-power registered output for a unit that hand-rolls its relation, as `Pump` still does).
- **BREAKING: `SurrogateSpec.functional_form` is an open string and `schema_version` is now `0.0.2`.** The form names a relationship *builder* registered in `flexops.core.ops_block._RELATION_BUILDERS`, so a new relationship shape never needs a schema revision again; an unregistered name is rejected when the model is built, with the known forms listed, rather than when the config is validated. `MIGRATIONS` gains its first entry — a `0.0.1` document loads and is re-stamped, since the widening is backward compatible — and the exported JSON Schema is regenerated. The reserved `"nn"`/`"arima"`/`"multiconvex"` values are gone; they no longer need reserving.
- **`SurrogateSpec.coefficients` keys are now product terms**, so one builder covers every polynomial relationship: a key is a `*`-separated product of input variable names, each optionally raised to an integer power with `^`, plus the reserved `intercept`. `"flow_out"` is linear, `"flow_out^2"` quadratic, `"flow_out*outlet_state.pressure"` the cross term of an expanded bilinear form. Coefficients (not `input_variables`) now determine which terms exist — previously a linear relationship took one coefficient per declared input and could not express a cross term at all. Every factor is resolved on the unit (dotted paths into a state block work) and normalized by its own units, so each coefficient is read in **the relationship's target's own units** over the product of its factors' units (kW for a power draw; whatever a non-power target is in otherwise — see the swap generalization below).
- **BREAKING: `OpsBlockData.swap_energy_relation` is gone, replaced by `register_relation`/`swap_relation`.** The swap is no longer power-specific: `register_relation(constraint, target)` declares any relationship a unit builds as swappable (an unregistered constraint — a mass balance, any conservation law — can never be swapped: there is no naming convention to accidentally satisfy), and `swap_relation(relation_name, surrogate)` replaces it in place, resolving units from the relation's own target rather than assuming kW. Every constant-intensity unit registers its own energy relation automatically; `SIDOBlock`/`ReverseOsmosis` additionally register `split_definition` (recovery/flux) and `Tank` its `level_definition` (fill geometry) — conservation constraints on both are deliberately not registered. `Pump`'s default relation is folded onto the shared `add_constant_intensity_relation` path (previously hand-rolled as `power_eq` with a mutable `Param`), so it is renamed to `power_electrical_relation`, its intensity becomes a fixed, regressable `Var`, and it is swappable for the first time; the `hydraulic` power law is untouched (a physical relationship, not an intensity, and not registered). `flexparameterize.apply.ApplyReport.swapped_units: list[str]` is replaced by `swapped_relations: dict[str, list[str]]` (unit -> relation names), and `apply_to_model`'s `surrogates=` values may now be a `{relation_name: spec}` mapping to swap a unit's *other* registered relations (an RO skid's recovery, a tank's geometry) instead of its energy draw, mixed freely with the plain-spec form across units in one call.
- **The relation-builder registry is not limited to polynomials.** A builder is `(unit, surrogate, target) -> body`, where `body(t)` is any Pyomo-expressible, dimensionless function of the unit's own variables — a ratio, a softplus/ICNN forward pass, a lag polynomial that returns `pyomo.environ.Constraint.Skip` for horizon points its lag does not reach — and may attach its own auxiliary Vars/Constraints, which a later re-swap deactivates alongside the relation itself. Registering a new form is a `flexops.core.ops_block._RELATION_BUILDERS` entry, never a config-schema change.

### Added

- **`quadratic`, `bilinear` and `polynomial` relationships**, alongside the existing `linear`. All four are built by one rule, `target[t] == c0 + Σ_k c_k Π_j x_kj[t]^n_kj`, and differ only in the term degree they admit (`POLYNOMIAL_FORMS`: 1, 2, 2, unbounded) — which is what turns a mislabelled relationship into an error instead of a silent surprise. `bilinear` is the *expanded* form: a constant, each input on its own, and their cross term, which is how a unit's net draw is modelled as a function of outlet flow and outlet pressure together. `flexparameterize.apply_to_model` attaches any of them to a live unit through the same `surrogates=` argument and the same in-place swap as before.
- **`flexops.core.registration.RelationRecord`/`IORegistry.relations`** and **`iter_swapped_relations(model)`**: a whole-model, O(registered relations) debugging/reporting aid answering "what in this model differs from its defaults?" for a model built any way (config, by hand, or `apply_to_model`) — not a required step on any build or apply path, and not a detector of changes made outside `swap_relation`.
- **`flexcore.config.io.load_surrogate_source`** and the new `SurrogateSpec.source` field: a relationship may live in a JSON sidecar supplying `coefficients`/`input_variables`/`output_variables` instead of being inlined in the config. A relative path resolves against the config file's own directory, and `load_model_config` fills every unit's surrogate in at the boundary, so nothing downstream sees a half-loaded relationship.

- **`flexparameterize`: the parameterization pipeline, in both directions.** `tabular data -> tag aliasing -> sufficiency validation -> regression -> {apply to model | emit config}` (architecture §5, R10). New public API: `TagMap`/`TagReport`/`model_alias` (`tags.py`, source-column to dotted `plant.unit.variable` aliasing, JSON-loadable, `difflib` suggestions for unmapped columns and no new dependencies); `check_sufficiency`/`SufficiencyReport`/`IOPairStatus` (`validate.py`, per-registered-IO-pair coverage, non-null counts and `DatetimeIndex` alignment — it reports, it never raises); `ConstantIntensityRegressor` (`regression/constant.py`, `intensity = mean(power / flow)` after dropping null and zero-flow rows, with `r2`/`rmse`/`n_samples`/`data_window`); `emit_model_config` (`emit.py`, fit -> a `ModelConfig` that `build_model` rebuilds the parameterized model from, with provenance carrying the fit metrics, data window and the `flex-pse`/`pyomo`/`pandas` versions read at emit time); and `apply_to_model`/`ApplyReport` (`apply.py`, fit -> an in-place mutation of a **live** model: registered parameters are fixed at their fitted values and a richer-than-constant-intensity relationship deactivates the unit's `power_electrical_relation` and attaches an equality built from the `SurrogateSpec`, on the same unit object with its ports and arcs untouched). Both directions consume the same `SurrogateSpec` from the same regressor, so they cannot disagree; `apply_to_model` raises `FlexDataError` up front on insufficient data, since it mutates a real model. Both also accept a hand-built `SurrogateSpec` directly — a vendor curve or datasheet coefficient needs no data, no sufficiency check and no regressor — and `apply_to_model`'s `surrogates=` and fit-from-data paths mix freely across units in one call. Nothing in the package assumes a historian: any tabular source works once its columns are mapped.
- **Docs**: `docs/how_to/parameterize_from_data.md` (the pipeline stage by stage, both terminal directions, and the no-fit path), `docs/reference/flexparameterize/index.rst`, and a new `docs/reference/glossary.md` defining **zero-degree-of-freedom regression** and **model alias**.

- **`NetworkBlockData.add_subset_aggregate(plants, var_name, *, name=None, replace=True)`**: sums a time-indexed quantity (looked up per plant via `find_component`) across a caller-chosen subset of a network's plants — e.g. one building's power draw within a larger campus — building a `Var`/`Constraint` pair (defaulting to `aggregate_{var_name}`/`eq_aggregate_{var_name}`). A plant missing `var_name` is skipped with a logged warning. Calling again with the same `name` updates the existing Constraint's body in place (never deleting it, conventions §9); pass `replace=False` to instead log a warning and leave the existing aggregate untouched. Distinct from the network's own always-every-plant totals (architecture §3.3/R7), which this does not affect.
- **`flexops.logic.register_parallel_group(units, *, then="on")`**: manually declares >= 2 units as a parallel/degenerate hierarchy group, for units the caller knows are interchangeable or otherwise hierarchically related but that `detect_parallel_trains`'s automatic class/config/connectivity predicate misses. Chains `add_conditional` over every consecutive pair rather than re-implementing implication logic, returning the `len(units) - 1` attached `conditional` Constraints. Raises `FlexConfigError` for fewer than two units or a repeated unit.
- **`CostReport` names its own currency.** `report_cost` now returns a `CostReport` with a `currency: str` field (`str(base_currency)` — the tariff sheet's basis when a tariff is given, else the configured `currency`), so a report is self-describing away from the costing block that produced it. Docstrings that hardcoded `($)` are corrected accordingly: the report dataclasses, the nine cost `Var`/`Param` `doc=` strings (which already carried the currency in their `units=`), and `CostingConfig.fixed_operating_cost`, which claimed "in dollars" but is denominated in whatever basis is in force. `schema_version` is unchanged (only a `description` string moved); exported JSON Schema regenerated.
- **`OpsBlockData.create_stream_naming_convention()` and a `naming_dict` argument on every IO-topology base's `build()`** (`SISOBlock`/`SIDOBlock`/`DIDOBlock`). Each base carries its generic role -> Pyomo component name mapping as `_component_names` and registers it at the top of `build()`; a physical subclass renames any subset by spreading that default and passing the result up (`super().build(naming_dict={**SIDOBlockData._component_names, "flow_in": "feed", ...})`, as `ReverseOsmosis` does for `feed`/`permeate`/`brine`/`recovery`). Everything the unit builds or looks up resolves through `_named()`; ports are never renamed.
- **`Combustor.air_to_fuel_ratio`** (default 9.5, dimensionless): volumes of combustion air entrained per unit volume of fuel gas, a fixed and regressable scalar Var that sets the flue-gas volume. An IC-design property — estimate or model it externally rather than deriving it here. Defined as air-per-fuel (a multiplier) rather than the reciprocal fuel-per-air so the mass balance stays **linear** even once a design mode or regression unfixes it.

### Removed

- **BREAKING: `dens_mass` is no longer a state variable on either property package, and `SimpleAqueousFlow`'s `fixed_density`/`density` config options are gone.** No unit model needed density — it was structural boilerplate inherited from WaterTAP's `prop_ZO` pattern, and carrying it only added a state variable to fix. `SimpleAqueousFlow` state blocks now carry `flow_vol_phase` plus the opt-in `pressure`/`temperature`; `SimpleGasFlow` carries `flow_vol_phase`/`pressure`/`temperature`. Callers passing `fixed_density=`/`density=` (including `examples/api_freeze.py`, the frozen-API tripwire script, and the `properties` block of a persisted config) must drop those keys.
- **BREAKING: `Combustor.outlet_density_eq` is gone**, along with the isobaric ideal-gas density correction it imposed — there is no longer a density state variable to correct. The outlet's temperature is still fixed at `flue_gas_temperature`.

### Added

- **`PlantBlock`/`NetworkBlock` now aggregate registered fuel usage into `total_fuel_usage[fuel_name, t]`** (m³/hr), alongside the existing `total_electrical_power`/`total_thermal_power`/`total_product`. Follows the `total_product` pattern: keyed by fuel name (there is no `FuelKind` enum), deferred and re-entrant like the other aggregates, and a network sums each contributing plant's own total rather than re-walking its units (no double-counting).

### Added

- **`Combustor`: the first `SimpleGasFlow` unit model — an arbitrary number of gas inlets mixed into one flue-gas outlet, exporting electrical power.** Every unit model shipped until now moved water, built on a single-`property_package` IO-topology base (`SISOBlock`/`SIDOBlock`/`DIDOBlock`). A combustor's inlet count is a config option (`inlet_names`), so no fixed-arity base fits — `Combustor` subclasses `flexops.core.ops_block.OpsBlockData` directly and hand-writes its own ports, mixing mass balance, and energy relation, the way `BatteryModel` does. Deviates from the earlier `Combustor(SIDOBlock)` sketch in architecture §3.4/the M09 plan; that table is updated. Delivered:
  - **`power_electrical[t]` is signed negative and upper-bounded at 0** — a combustor *exports* power, following the `BatteryModel` discharge convention, so plant aggregation nets generation against load with no per-unit sign-flipping. `docs/explanation/energy_nomenclature.md`'s sign rule now covers generation as well as storage.
  - **Two flow-to-power relations, resolved automatically** from whether every configured inlet was given a heating value (never a user-selected mode): `power_electrical[t] = -efficiency * Σ heating_value_i * flow_in_i[t]` when every inlet has one, else `power_electrical[t] = -energy_intensity * Σ flow_in_i[t]`. A partial `heating_values` mapping, or an option the resolved relation would ignore (`efficiency` under constant intensity, `energy_intensity` under heating value), raises `FlexConfigError` naming the field. Both build the Constraint `power_electrical_relation` — the same swap-contract name every other unit uses, so `FlexParameterize`'s constraint swap works unmodified.
  - **Flue gas**: every configured inlet is a *fuel* stream; combustion air is not modeled as an inlet, so `flow_out[t] == (1 + air_to_fuel_ratio) * Σ flow_in_i[t]` — the fuel burned plus the air it entrains. Plus `inlet_state_equality_<state>[t, name]` tying every non-reference inlet's pressure/temperature to the reference inlet's (a mixing node shares intensive state). Only the reference inlet's non-flow states are registered as IO inputs — registering every inlet's would over-determine the model, since these equalities already pin the rest.
  - **Outlet state**: pressure passes through from the reference inlet; temperature is fixed at the new `flue_gas_temperature` config option.
  - New `flexops.testing.dummy_gas_time_block(n)` — the `SimpleGasFlow` twin of `dummy_time_block`, needed because `SimpleGasFlow`'s always-on state blocks give a gas unit a different degrees-of-freedom accounting than the aqueous default.
  - Registering fuel usage for costing (`register_fuel_usage`) is deliberately **out of scope** for this unit — pinned by a test so a later change to that is deliberate, not incidental.

- **The public API is frozen, and the whole model builds from one config file (M09).** New `examples/api_freeze.py` — the PLAN.md §2 script — runs top to bottom and solves, guarded by `src/flexops/tests/test_api_freeze.py`: from now on, a change that forces an edit to that script is a **breaking change**. Its config-driven twin `examples/api_freeze_config.json` builds through the new `fo.build_model(...)` and is held to the **same solved objective**. Delivered to get there:
  - **Composition (`fo.PlantBlock`, `fo.NetworkBlock`).** A `PlantBlock` is a collection of **unit** blocks (one facility, holding the arcs between its units); a `NetworkBlock` is a composition of **plant** blocks (R7) — a plant is never nested inside a plant. Both are thin IDAES `FlowsheetBlockData` subclasses forced to `dynamic=False`, with the `TimeBlock`'s ordered integer `Set` installed as their time domain **by reference** (`plant.time is time_block.time_index`; never Pyomo.DAE, R2). Each exposes `total_electrical_power[t]` / `total_thermal_power[t]` `Expression`s, and a network's totals are the sums of its **plants'** totals — never a second walk over their units, so no unit is double-counted. Aggregation is **deferred and re-entrant** (`_build_aggregates()` creates the Expression once and refreshes its body from the children present at each call), because the frozen script builds costing *and* the plant before any unit exists; `FlexCosting.cost_process()` now triggers it for every plant/network on the model, so the common path needs no user call. Neither block has a `replace_unit`: FlexParameterize mutates units in place. A plant can `register_product(var, name=..., quality=...)`; the network sums the amounts into `total_product[product, t]` and, where qualities are registered, requires **like-quality mixing** (`eq_product_quality`, the linear reading — a flow-weighted blend would make every mixing point bilinear). `NetworkBlock.add_link(name, source, destination)` constrains any two time-indexed quantities across plants (heat out vs. heating load, product out vs. feed in) — the network relates *quantities*, where a plant copies stream state with arcs. `time_block=` stays the primary, tested-first path on both; omitting it discovers the model's only `TimeBlock` and raises `FlexConfigError` on zero or several.
  - **IO-topology bases `SIDOBlock` (1→2) and `DIDOBlock` (2→2)**, joining M04's `SISOBlock`. `SIDOBlock` splits one feed into `outlet_a`/`outlet_b` with two constraints — conservation `flow_in == flow_out_a + flow_out_b` plus `split_definition` (`flow_out_a == split_fraction * flow_in`), since conservation alone leaves the split undetermined. `DIDOBlock` couples two streams through one `transfer_fraction` (`flow_out_a == (1 - f) * flow_in_a`, `flow_out_b == flow_in_b + f * flow_in_a`). Both ratios are fixed, **regressable** scalar `Var`s, so the topologies stay linear/LP-representable and the split is the natural regression target. `SIDOBlock` bounds its split only to a physical fraction and takes no window options; a physical subclass renames the split into its own vocabulary and narrows the window (see `ReverseOsmosis` below). Each base passes everything a stream carries other than flow through to *each* of its outlets; `OpsBlockData.add_pass_through_constraints` gains a `name_prefix=` so a multi-outlet topology's repeated calls do not collide on one component name.
  - **The physical zoo:** no intermediate `Separator`/`Electrolyzer` class (R6) — a physical unit subclasses the matching topology base directly and renames its generic roles (`flow_in`/`flow_out_a`/`split_fraction`/...) into its own vocabulary via a `_component_names` dict resolved through `OpsBlockData._named()`. `Exchanger(DIDOBlock)` and `ReverseOsmosis(SIDOBlock)` (`outlet_a` is `permeate`, and the split is **renamed** to `recovery` — `split_fraction` does not exist on the skid — bounded by the new `recovery_min`/`recovery_max` seawater window, which an inverted or unsatisfiable setting rejects with `FlexConfigError`).
  - **`ConstantEnergyIntensityModel(SISOBlock)`** — the generic "energy factor × flow" unit, and FlexOps' one building block for anything without a bespoke physical topology (a whole treatment plant as a single surrogate, as in the frozen script's `waterfacility.plant`). There is deliberately **no** `LinearRegressionModel` or other regression unit class (R11).
  - **One place builds a flow-to-energy relationship.** New `OpsBlockData.add_constant_intensity_relation(flow, kind=..., intensity=...)` declares the power draw, its intensity `Var` (`energy_intensity` / `thermal_intensity`, fixed and registered `regressable=True`), and the equality as the Constraint **`power_electrical_relation`** (resp. `power_thermal_relation`). That name is the documented **swap contract**: new `OpsBlockData.swap_energy_relation(surrogate, kind=...)` deactivates exactly it (never deletes — conventions §9) and attaches `power_<kind>_relation_fitted` built from a fitted `SurrogateSpec`, reusing the unit's existing registered variables so ports and arcs are untouched. One swap implementation, two callers: construction time (a config carrying a non-`constant_intensity` form) and, from M10, `flexparameterize.apply_to_model`. `linear` is the one fitted form v0 builds; the reserved `nn`/`arima`/`multiconvex` raise.
  - **`OpsBlockData.build_from_config(cfg, **kwargs)` is real** (a `NotImplementedError` stub since M03). It round-trips a path/mapping through the pydantic schema (so a raw dict is never passed on, conventions §4), resolves `cfg.unit_model_class` against `flexops.unit_models`, and merges construction options with the caller's runtime-only ones (`property_package`, `costing_package`), which win. An invalid config raises `pydantic.ValidationError` **unwrapped**, naming the offending field path.
  - **`fo.build_model(config)`** builds the TimeBlock, property package, `FlexCosting`, the network/plant/unit tree, its arcs, any declared external (DERMS) dispatch, and the objective from one validated `ModelConfig`. Arcs are declared but **not** expanded — applying `TransformationFactory("network.expand_arcs")` stays the caller's explicit step, in the config path as in the script. New `parse_quantity`/`parse_units` resolve the units a persisted config carries as data (`{"value": 0.5, "units": "kWh/m^3"}`, or `"15 min"` for the time step), closing the gap M03's `build_from_config` TODO flagged as the blocker; unknown unit tokens register as a currency, so `"USD/kWh"` parses without a costing block existing yet.
  - Fixtures `examples/data/tariff.json` (a tiny TOU sheet) and `examples/data/dr_events.json` (an empty DR program), which the frozen script loads by bare filename.
  - `docs/getting_started/ten_minutes.md` (new), a fleshed-out `docs/how_to/build_a_plant.md` (build order, the config conventions, multi-plant networks), the R2/R7 rationale in `docs/explanation/time_and_dynamics.md`, and reference pages for every new class. `BatteryModel` also gets the reference page M08 omitted (`sphinx-build -W` was failing on it).

### Changed

- **`parse_quantity` gained `strict=`, and `build_from_config` passes `strict=False`,** so a construction option written as a plain string in a persisted config (e.g. an enum member's name) reaches the unit's `ConfigValue` domain instead of being rejected as a malformed quantity. This restores `build_from_config`'s documented contract ("anything else passes through unchanged"). `TimeConfig.time_step` still parses strictly, so `"15 min"` keeps its loud error.
- **`Tank`'s `max_volume`/`initial_volume` now have defaults** (1000 m³ and 500 m³, half full) instead of being required. Needed so the frozen `fo.Tank(property_package=m.properties)` builds; a real tank is still always given its own sizing.
- **A `BatteryModel` with unit commitment on and no power rating now derives a 1C limit** (its whole capacity in one hour) instead of raising. The frozen script builds `BatteryModel(capacity=1 * pyunits.kWh, costing_package=...)` with no rating at all, and the semicontinuous `status` link needs a finite bound; giving **one** of `power_charge_max`/`power_discharge_max` without the other still raises. `test_status_requires_both_power_maxima` is renamed and its both-unset case replaced by one asserting the 1C fallback.
- **`BatteryModel`'s `unit_commitment.status` now defaults to `False`,** overriding the project-wide `True` default (`CONFIG.get("unit_commitment").set_default_value(...)`, the same pattern `SISOBlock`/`Combustor` use for `allow_pass_through`) instead of just inheriting it — a bare `BatteryModel(capacity=...)` now builds as a plain LP with no on/off binary. Opt in with `unit_commitment=UnitCommitmentConfig(status=True)`. The 1C power fallback above is decoupled from `status` so it applies either way — a battery with no explicit power rating is never left unbounded, on or off.
- **`PLAN.md` §2 and the frozen script import `Arc` from `pyomo.network`** (`m.waterfacility.tank_to_plant = Arc(...)`). The earlier `pyo.Arc` spelling names an API Pyomo has never had — `Arc` lives in `pyomo.network` and is not re-exported into `pyomo.environ` — so the script could not have run as written. Corrected at the source so `examples/api_freeze.py` stays byte-for-byte identical to PLAN.md §2, and recorded there alongside the existing slide-API corrections.
- `docs/explanation/time_and_dynamics.md`'s holdup example is written in the **backward** difference form the codebase actually uses (`V[t] = V[t-1] + dt * (...)`, conventions §2); it previously showed the forward form.
- `OpsBlockData._find_time_block` delegates to a new module-level `flexops.core.time_block.find_time_block(model)`, the one auto-discovery implementation now shared with `PlantBlock`/`NetworkBlock`.

### Added

- **Solvers are installed in CI.** New `solvers` optional dependency (`pip install -e ".[solvers]"`) pulls in the HiGHS wheel (`highspy`), and a new `.github/actions/setup-ipopt` composite action runs `idaes get-extensions` for IPOPT, caching the idaes binary directory keyed on OS + idaes version and exporting it to `PATH`. On Linux runners the action also apt-installs the LAPACK/BLAS/gfortran runtime libraries the IDAES `ubuntu2204` IPOPT build links against (absent from the ubuntu-24.04 image, where `ipopt` otherwise exits 127 on `liblapack.so.3`), and finishes by solving a one-variable NLP so a binary that cannot load its libraries fails in setup rather than mid-suite — `SolverFactory("ipopt").available()` only checks that the file exists, so `needs_ipopt` does not skip in that case. Both the `fast-tests` and `integration` CI jobs now use them, so `needs_highs`/`needs_ipopt` tests actually run on a PR instead of skipping.
- `BatteryModel` gains `soh` (state of health, default 0.85/mid-life) and a `soh_capacity_limit` constraint (`charge[t] <= soh * capacity`, independent of `soc_max`), plus `eta_charge`/`eta_discharge` are now fixed `Var`s (not plain config floats) — all three registered `regressable=True` (matching `Pump.efficiency`) so a future FlexParameterize regression can fit them from SCADA data: `power_charge`/`power_discharge` in, `charge` (now registered as the process output) out, `capacity` known. **Not part of the M08 spec** — added at explicit user request; see the class docstring's "Deviations from the milestone spec."
- `BatteryModel` gains `charge_leakage_rate` (self-discharge), a fixed `Var` in fraction-of-charge-per-day (default `0.0005`, i.e. 0.05%/day), registered `regressable=True` like `eta_charge`/`eta_discharge`/`soh`. `charge_balance` now subtracts `charge[t-1] * charge_leakage_rate * dt` each step. **Not part of the M08 spec** — added at explicit user request; see the class docstring's "Deviations from the milestone spec."
- **An energy price may vary over the horizon, and a bare number is now accepted.** `FlexCosting`'s `energy_prices` entries widen from a units-carrying scalar to any of three forms per carrier: a single value (flat over the horizon), an **array-like with one value per time point** (list/tuple/numpy array, read in time-index order), or a **Pyomo component indexed over the horizon** — so a price can be a mutable `Param` updated between rolling-horizon solves, or even a `Var`. An indexed price need not live on the TimeBlock's `time_index`, only have exactly one value per time point (read in its own index-set order). The native cost formula generalizes from `price × Σ_t quantity[t] × dt` to `Σ_t price[t] × quantity[t] × dt` (unchanged for a flat price, which is still factored out of the sum), in the in-objective constraint and in `report_cost`'s independent post-solve recomputation alike. A price with the **wrong number of values** raises `FlexConfigError` at `FlexCosting` construction — the earliest point the horizon length is known — naming both counts; a `Mapping` price is rejected outright, since iterating it would cost its keys. **A bare number is no longer rejected** (it previously raised "has no units"): it is read in the currency over the carrier's metered quantity — `kWh` for a power carrier, `m³` for a fuel — so `{"electrical": 0.12}` means $0.12/kWh and `{"natural_gas": 0.50}` means $0.50/m³. A price that *does* carry units is passed through untouched, so a mis-dimensioned price still fails the unit-consistency check rather than being silently reinterpreted. `CostingConfig`'s `PriceSpec.value` widens to `float | list[float]` (non-empty) to mirror it; the length-vs-horizon check is **not** enforceable in the persisted schema (deriving the number of time points needs a `TimeConfig.time_step` string parser, which does not exist yet) and remains the runtime one. `schema_version` stays `0.0.1`: widening a field is backward-compatible and every existing config still validates. Exported JSON Schema regenerated.
- **A tariff is now optional: flat energy prices, several tariff files, and EECO as a soft dependency.** `FlexCosting` gains an `energy_prices` config entry mapping a carrier or fuel name (`"electrical"`, or a registered fuel) to a **units-carrying** price (e.g. `0.12 * currency_units("USD") / pyunits.kWh`); that carrier is then billed natively as `price × Σ_t quantity[t] × dt` and never sent to EECO. A flat price **wins over** a tariff covering the same carrier, so tariff-priced electricity and a flat-priced fuel can be mixed. `tariff_file`/`tariff` relax from *exactly one* to *at most one* and now also accept **several** sources — a list to merge, or a mapping of EECO utility (`"electric"`/`"gas"`) to source to merge *and* assign each file to a utility (keeping only that utility's rows, so a sheet's stray rows cannot leak into the bill) — via the new `merge_tariffs`, which raises rather than silently doubling a charge two sources both define. Several files always collapse to one `rate_data` frame whose `utility` column selects rows per leg; the covered utilities are recorded so an unpriced carrier raises `FlexConfigError` **naming the carrier** instead of contributing a silent `$0`. The `eeco` import is now **soft**: `import flexops` and a fully flat-priced build/solve/`report_cost` work with EECO absent, and any tariff path raises `FlexConfigError` naming both remedies (install `eeco`, or price the carrier flat). New `currency_units(symbol="USD")` supplies the Pyomo currency for writing flat prices and is the base currency when no tariff sets one (new `currency` config entry). `CostingConfig` mirrors all of it (`tariff_source` widened to `str | list | dict | None`, new `energy_prices` of `PriceSpec` (`value` + `units` string), `currency`, plus a validator requiring a tariff or at least one price); exported JSON Schema regenerated.
- **Annualization takes a cost of capital.** New `interest_rate` config entry (default `None`) on `FlexCosting`/`CostingConfig`. The capital recovery factor is now built on a single `effective_rate` Param: `discount_rate` alone when `interest_rate` is unset — so existing configs annualize **exactly as before** — and the real rate `(1 + interest_rate) / (1 + discount_rate) - 1` when both are given. An effective rate of `0` still falls back to straight-line `1/lifetime_years`; an effective rate `<= -1` or a non-positive `lifetime_years` now raises `FlexConfigError` (the `> 0` bound `lifetime_years`' description already claimed was never enforced).

### Changed

- **Monthly-assessed tariff charges are prorated to sub-monthly horizons (this changes cost values).** A demand charge and a tariff's fixed (customer) charge are billed per calendar month, but flex-pse billed them in **full** on any horizon — a 24-hour run paid the whole `$150`/month customer charge and the whole `$21.50 + $19.00` per-kW monthly demand charges. With the new `prorate_monthly_charges` (default **`True`**, on `FlexCosting` and `CostingConfig`) both are scaled by the new `monthly_scale_factor` — horizon length over the real length of the calendar month it starts in. Energy charges are never scaled, a demand charge marked `"assessed": "daily"` is left alone (it is already at horizon granularity), and a full-month horizon is unaffected (the golden `$14,085.00` monthly bill is unchanged). `prorate=False` on `add_electricity_cost`/`add_fuel_cost`/`add_operating_cost`/`evaluate_cost`/`evaluate_fuel_cost` restores the old numbers. The headline load-shifting regression constant is re-recorded accordingly (`1467.388888888889` → `147.4964157706093`, a 24-h horizon of a 31-day month). Prorating is applied to the charge **rates** before EECO sees them, leaving EECO's tiered-surcharge arithmetic untouched; flex-pse does this itself because the `get_charge_dict` path exposes no equivalent option (EECO's `calculate_cost` adds the customer charge whole, and its `demand_scale_factor` is suppressed for charges spanning `<= 1` day — which, since EECO clips charge-key dates to the horizon, would silently include *every* monthly charge on a one-day horizon, the very case prorating exists for). `OperatingCostHandles` gains `customer_charge` and `scale_factor`.
- `FlexCosting`'s flat-price, fuel-price, and scalar-cost line items share one `price × Σ_t series[t] × dt` builder, which integrates over the *series'* own index set and raises `FlexConfigError` if that is not the model's `time_index` — so costing a batch or cyclic unit on a separate time index is a loud error rather than a silently wrong bill (supporting it needs the power/fuel aggregation and the EECO bridge changed first, as both assume one uniform grid).
- **What crosses the EECO cost boundary is now a bare magnitude, not a units-carrying expression (no cost values change).** EECO applies its unit conversion as a plain float factor and constrains its own *dimensionless* Vars to the series it is handed (`electric_converted[t] == series[t] * factor`), so handing it kW / m³/hr expressions left EECO's internal constraints dimensionally inconsistent — a whole-model `assert_units_consistent`, the standard Pyomo/IDAES diagnostic, failed on any tariff-priced model (48 constraints on a 24-step model with one fuel). `opex.eeco_aggregate_electrical_power` is now **dimensionless** (the kW-converted aggregate divided by its units), and the fuel legs gain the matching `opex.fuel_<name>.eeco_aggregate_fuel_usage` instead of passing the m³/hr `aggregate_fuel_usage` Reference straight through. `aggregate_power`/`aggregate_fuel_usage` keep their units, so nothing user-facing moves. The `power`/`electrical_power`/`fuel_power` arguments of `add_electricity_cost`/`add_fuel_cost`/`add_operating_cost` are documented accordingly: pass a bare kW / m³/hr magnitude.

- Added the full versioned config schema (`flexcore.config.schema`, pydantic v2, decision R3): `IOVariableSpec`, `SurrogateSpec`, `ExternalDispatchSpec`, `UnitCommitmentConfig`, `UnitConfig`, `PlantConfig`, `NetworkConfig`, `TimeConfig`, `CostingConfig` (with a `DRConfig` container slot), and the top-level `ModelConfig` (mandatory semantic-version `schema_version`, exactly-one-of `network`/`plant`). Added `flexcore.config.io` (`load_model_config`/`dump_model_config` with JSON as the only on-disk format plus direct dict input, a `MIGRATIONS` table, and `export_json_schemas` with an optional `filename` for side-by-side schema versions) and the checked-in JSON Schema at `src/flexcore/config/schemas/model_config.schema.json`, whose descriptions are exported as plain single-line text (no newlines or section-sign codes; wrapping is the doc builder's job). Added `flexcore.nomenclature` (the `POWER_ELECTRICAL`/`POWER_THERMAL` constants and `PowerKind`). New docs: config-schema and energy-nomenclature explanation pages, `flexcore` config/nomenclature/exceptions reference sections, and a `flexops.properties` reference page (M03).

- Added the public, shipped `flexops.testing.UnitModelTestHarness`: every unit-model milestone (and any user writing a custom unit model) subclasses it instead of hand-writing the build/units-consistency/registration/energy-naming/degrees-of-freedom/solve/solution checks (`test_build`, `test_units_consistent`, `test_io_registration`, `test_energy_naming`, `test_dof` on the `unit` tier; `test_solve`, `test_solution` on the `component` tier, skipping cleanly if `flexcore.solvers.get_solver` is unavailable). Added `flexops.testing.dummy_time_block(n=3)`, a throwaway `TimeBlock` + `SimpleAqueousFlow` model reused by the M14 docs generator. Added `OpsBlockData.add_pass_through_constraints(inlet, outlet, *, exclude_vars=())`: a generic inlet-to-outlet pass-through for every non-excluded, non-fixed state variable (e.g. `dens_mass` under `fixed_density` is skipped automatically), gated by `self.config.allow_pass_through`; it resolves each port's sibling `"{port}_state"` block rather than the port's own `vars` mapping, since the latter are auto-generated `Reference`s carrying a leaky extra `UnindexedComponent_set` dimension. Added `SISOBlock` (`flexops.unit_models.base`), the first IO-topology base class (architecture §3.4/R6): builds the inlet/outlet ports via the inherited `add_stream_ports`, then its per-stream pass-through via `add_pass_through_constraints` with no exclusions (flow's pass-through is itself a pass-through equality, named `pass_through_flow_vol_phase_eq`); `SISOBlock` overrides the inherited `allow_pass_through` default to `True` so the topology is well-posed out of the box. Added `SimpleAqueousFlow.get_flow_basis_var_name()`/`SimpleGasFlow.get_flow_basis_var_name()` (both return `"flow_vol_phase"`), letting callers exclude "the flow" from a generic pass-through without hardcoding a property-package-specific name. Added the first two physical unit models on top of the SISO base: `Pump(SISOBlock)` (`power_electrical[t] = energy_intensity * inlet flow`, dimensionally exact kWh/m³ × m³/hr = kW; carries a `.. todo::` note for a future detailed power law, e.g. density·flowrate·head/efficiency, not built here) and `Tank(SISOBlock)` (holdup difference equation `volume[t+1] = volume[t] + dt*(in - out)` over `t = 0..N-2`, converting the whole flow-difference expression rather than assuming the flow basis's units). `Tank` now distinguishes `max_volume` (the maximum *possible* tank volume -- fixed by prior investment or space constraints, a static upper bound) from `capacity` (the *chosen* volume, a fixable design `Var` now bounded `(min_volume, max_volume)` so a design-mode solve can never exceed the maximum possible size). Added a bounded `level[t]` Var (`level_min`/`level_max` config, default `(0.0, 1.0)`) defined by `level_definition[t]: volume[t] == level[t] * capacity` -- the fractional fill relative to the *chosen* capacity, preventing the tank from draining all the way down or overfilling; this is linear (LP) in operations mode (`capacity` fixed) but bilinear (**NLP**) in design mode (`capacity` free), so design-mode solves of a model containing a tank need IPOPT or a `flexschedule.SolveSequence`, not HiGHS. `Tank` forces `unit_commitment.status = False` regardless of what a caller passes -- a tank has no on/off status, the canonical example of a physical subclass turning off a base capability (R6). New docs: `flexops.testing` and `flexops.unit_models` (with the `unit_model.rst` autosummary template, a `flexops-unit-tables` TODO placeholder for M14) reference pages (M04).

### Fixed

- **`import flexops.testing` no longer fails on a standard install.** `flexops.testing` imports `pytest` at module level (`UnitModelTestHarness` uses `pytest.mark`/`pytest.skip`/`pytest.approx`), but `pytest` was listed only in the `dev` extra, so `pip install flex-pse` followed by `import flexops.testing` raised `ModuleNotFoundError: No module named 'pytest'`. New `testing` optional dependency: users subclassing the harness in their own test suites install `pip install "flex-pse[testing]"` (contributors already get it from `dev`). Installing without it still works — `flexops.testing` is the only module that needs it. The CI `standard-install` job's bare-install smoke-import list drops `flexops.testing` accordingly and gains a second step that installs `flex-pse[testing]` and imports it, so both paths are covered.
- `OpsBlock` now coerces an explicit `unit_commitment=None` to an all-defaults `UnitCommitmentConfig` in `build()` (Pyomo skips `ConfigValue` domains for `None`, so the domain-level coercion never ran).
