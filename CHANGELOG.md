# Changelog

All notable changes to this project are documented in this file.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- **Solvers are installed in CI.** New `solvers` optional dependency (`pip install -e ".[solvers]"`) pulls in the HiGHS wheel (`highspy`), and a new `.github/actions/setup-ipopt` composite action runs `idaes get-extensions` for IPOPT, caching the idaes binary directory keyed on OS + idaes version and exporting it to `PATH`. On Linux runners the action also apt-installs the LAPACK/BLAS/gfortran runtime libraries the IDAES `ubuntu2204` IPOPT build links against (absent from the ubuntu-24.04 image, where `ipopt` otherwise exits 127 on `liblapack.so.3`), and finishes by solving a one-variable NLP so a binary that cannot load its libraries fails in setup rather than mid-suite — `SolverFactory("ipopt").available()` only checks that the file exists, so `needs_ipopt` does not skip in that case. Both the `fast-tests` and `integration` CI jobs now use them, so `needs_highs`/`needs_ipopt` tests actually run on a PR instead of skipping.
- `BatteryModel` gains `soh` (state of health, default 0.85/mid-life) and a `soh_capacity_limit` constraint (`charge[t] <= soh * capacity`, independent of `soc_max`), plus `eta_charge`/`eta_discharge` are now fixed `Var`s (not plain config floats) — all three registered `regressable=True` (matching `Pump.efficiency`) so a future FlexParameterize regression can fit them from SCADA data: `power_charge`/`power_discharge` in, `charge` (now registered as the process output) out, `capacity` known. **Not part of the M08 spec** — added at explicit user request; see the class docstring's "Deviations from the milestone spec."
- `BatteryModel` gains `charge_leakage_rate` (self-discharge), a fixed `Var` in fraction-of-charge-per-day (default `0.0005`, i.e. 0.05%/day), registered `regressable=True` like `eta_charge`/`eta_discharge`/`soh`. `charge_balance` now subtracts `charge[t-1] * charge_leakage_rate * dt` each step. **Not part of the M08 spec** — added at explicit user request; see the class docstring's "Deviations from the milestone spec."
- **An energy price may vary over the horizon, and a bare number is now accepted.** `FlexCosting`'s `energy_prices` entries widen from a units-carrying scalar to any of three forms per carrier: a single value (flat over the horizon), an **array-like with one value per time point** (list/tuple/numpy array, read in time-index order), or a **Pyomo component indexed over the horizon** — so a price can be a mutable `Param` updated between rolling-horizon solves, or even a `Var`. An indexed price need not live on the TimeBlock's `time_index`, only have exactly one value per time point (read in its own index-set order). The native cost formula generalizes from `price × Σ_t quantity[t] × dt` to `Σ_t price[t] × quantity[t] × dt` (unchanged for a flat price, which is still factored out of the sum), in the in-objective constraint and in `report_cost`'s independent post-solve recomputation alike. A price with the **wrong number of values** raises `FlexConfigError` at `FlexCosting` construction — the earliest point the horizon length is known — naming both counts; a `Mapping` price is rejected outright, since iterating it would cost its keys. **A bare number is no longer rejected** (it previously raised "has no units"): it is read in the currency over the carrier's metered quantity — `kWh` for a power carrier, `m³` for a fuel — so `{"electrical": 0.12}` means $0.12/kWh and `{"natural_gas": 0.50}` means $0.50/m³. A price that *does* carry units is passed through untouched, so a mis-dimensioned price still fails the unit-consistency check rather than being silently reinterpreted. `CostingConfig`'s `PriceSpec.value` widens to `float | list[float]` (non-empty) to mirror it; the length-vs-horizon check is **not** enforceable in the persisted schema (deriving the number of time points needs a `TimeConfig.time_step` string parser, which does not exist yet) and remains the runtime one. `schema_version` stays `0.0.1`: widening a field is backward-compatible and every existing config still validates. Exported JSON Schema regenerated.
- **A tariff is now optional: flat energy prices, several tariff files, and EECO as a soft dependency.** `FlexCosting` gains an `energy_prices` config entry mapping a carrier or fuel name (`"electrical"`, or a registered fuel) to a **units-carrying** price (e.g. `0.12 * currency_units("USD") / pyunits.kWh`); that carrier is then billed natively as `price × Σ_t quantity[t] × dt` and never sent to EECO. A flat price **wins over** a tariff covering the same carrier, so tariff-priced electricity and a flat-priced fuel can be mixed. `tariff_file`/`tariff` relax from *exactly one* to *at most one* and now also accept **several** sources — a list to merge, or a mapping of EECO utility (`"electric"`/`"gas"`) to source to merge *and* assign each file to a utility (keeping only that utility's rows, so a sheet's stray rows cannot leak into the bill) — via the new `merge_tariffs`, which raises rather than silently doubling a charge two sources both define. Several files always collapse to one `rate_data` frame whose `utility` column selects rows per leg; the covered utilities are recorded so an unpriced carrier raises `FlexConfigError` **naming the carrier** instead of contributing a silent `$0`. The `eeco` import is now **soft**: `import flexops` and a fully flat-priced build/solve/`report_cost` work with EECO absent, and any tariff path raises `FlexConfigError` naming both remedies (install `eeco`, or price the carrier flat). New `currency_units(symbol="USD")` supplies the Pyomo currency for writing flat prices and is the base currency when no tariff sets one (new `currency` config entry). `CostingConfig` mirrors all of it (`tariff_source` widened to `str | list | dict | None`, new `energy_prices` of `PriceSpec` (`value` + `units` string), `currency`, plus a validator requiring a tariff or at least one price); exported JSON Schema regenerated.
- **Annualization takes a cost of capital.** New `interest_rate` config entry (default `None`) on `FlexCosting`/`CostingConfig`. The capital recovery factor is now built on a single `effective_rate` Param: `discount_rate` alone when `interest_rate` is unset — so existing configs annualize **exactly as before** — and the real rate `(1 + interest_rate) / (1 + discount_rate) - 1` when both are given. An effective rate of `0` still falls back to straight-line `1/lifetime_years`; an effective rate `<= -1` or a non-positive `lifetime_years` now raises `FlexConfigError` (the `> 0` bound `lifetime_years`' description already claimed was never enforced).

### Changed

- **Monthly-assessed tariff charges are prorated to sub-monthly horizons (this changes cost values).** A demand charge and a tariff's fixed (customer) charge are billed per calendar month, but flex-pse billed them in **full** on any horizon — a 24-hour run paid the whole `$150`/month customer charge and the whole `$21.50 + $19.00` per-kW monthly demand charges. With the new `prorate_monthly_charges` (default **`True`**, on `FlexCosting` and `CostingConfig`) both are scaled by the new `monthly_scale_factor` — horizon length over the real length of the calendar month it starts in. Energy charges are never scaled, a demand charge marked `"assessed": "daily"` is left alone (it is already at horizon granularity), and a full-month horizon is unaffected (the golden `$14,085.00` monthly bill is unchanged). `prorate=False` on `add_electricity_cost`/`add_fuel_cost`/`add_operating_cost`/`evaluate_cost`/`evaluate_fuel_cost` restores the old numbers. The headline load-shifting regression constant is re-recorded accordingly (`1467.388888888889` → `147.4964157706093`, a 24-h horizon of a 31-day month). Prorating is applied to the charge **rates** before EECO sees them, leaving EECO's tiered-surcharge arithmetic untouched; flex-pse does this itself because the `get_charge_dict` path exposes no equivalent option (EECO's `calculate_cost` adds the customer charge whole, and its `demand_scale_factor` is suppressed for charges spanning `<= 1` day — which, since EECO clips charge-key dates to the horizon, would silently include *every* monthly charge on a one-day horizon, the very case prorating exists for). `OperatingCostHandles` gains `customer_charge` and `scale_factor`.
- `FlexCosting`'s flat-price, fuel-price, and scalar-cost line items share one `price × Σ_t series[t] × dt` builder, which integrates over the *series'* own index set and raises `FlexConfigError` if that is not the model's `time_index` — so costing a batch or cyclic unit on a separate time index is a loud error rather than a silently wrong bill (supporting it needs the power/fuel aggregation and the EECO bridge changed first, as both assume one uniform grid).
- **What crosses the EECO cost boundary is now a bare magnitude, not a units-carrying expression (no cost values change).** EECO applies its unit conversion as a plain float factor and constrains its own *dimensionless* Vars to the series it is handed (`electric_converted[t] == series[t] * factor`), so handing it kW / m³/hr expressions left EECO's internal constraints dimensionally inconsistent — a whole-model `assert_units_consistent`, the standard Pyomo/IDAES diagnostic, failed on any tariff-priced model (48 constraints on a 24-step model with one fuel). `opex.eeco_aggregate_electrical_power` is now **dimensionless** (the kW-converted aggregate divided by its units), and the fuel legs gain the matching `opex.fuel_<name>.eeco_aggregate_fuel_usage` instead of passing the m³/hr `aggregate_fuel_usage` Reference straight through. `aggregate_power`/`aggregate_fuel_usage` keep their units, so nothing user-facing moves. The `power`/`electrical_power`/`fuel_power` arguments of `add_electricity_cost`/`add_fuel_cost`/`add_operating_cost` are documented accordingly: pass a bare kW / m³/hr magnitude.

### Added

- **`FlexCosting` extensibility groundwork (additive; no cost values change).** `opex.total_operating_cost` now sums over an explicit list of category sub-total names (`electricity_cost`/`fuel_cost`/`fixed_operating_cost`/`scalar_cost`) instead of a hardcoded four-term expression, so a future cost category is added by building its sub-total `Var` and appending one name. `FlexCosting.register_scalar_cost` gains an optional keyword-only `unit=` that records the owning unit block on the returned `ScalarCostSpec` (default `None`), so per-unit maintenance/chemical/labor attribution can be surfaced later without a signature change.
- **`FlexCosting` hardening — Var+Constraint model, arbitrary energy carriers, non-energy scalar costs, annualization.** Every quantity `FlexCosting` exposes is now a decision-visible `Var` defined by an `eq_<name>` equality `Constraint` (not a bare `Expression`): aggregate power, each cost line item, the annualized cost, and the totals. `cost_process()` now aggregates **all** registered power draws into an indexed `aggregate_power[t, carrier]` (kW) — `"electrical"` and one carrier per distinct **thermal** temperature (`"thermal@<T>K"`; duties at different temperatures are never summed). Every draw is normalized to kW with `pyunits.convert` at aggregation, so a non-power draw fails loudly. The electrical series is normalized to EECO's expected units via an explicit `opex.eeco_*` Var + constraint before it is handed to EECO. `declare_power`/`register_power` take an optional `temperature` (required for `THERMAL`), carried on `PowerRecord`. **Fuel is a metered volumetric flow, not a power** (see the separate entry below). `FlexCosting.register_scalar_cost(name, quantity, price, quantity_units)` adds a wholly **non-EECO** operating-cost category for flows/supplies/products (`price × Σ quantity × dt`; a signed price supports revenue credits), exposed as `opex.scalar_cost` in `total_operating_cost`. Annualization: `CostingConfig.lifetime_years` + `discount_rate` form a `capital_recovery_factor` and an `annualized_cost` Var ($/year, opex scaled horizon→year + capex×CRF). `report_cost` gains an `operating.scalar` field and sums each fuel's post-hoc EECO bill. A unit-consistency check reconciles every operating-cost line item onto the tariff currency or raises `FlexConfigError`. New `ScalarCostSpec` exported from `flexops.costing`. Exported JSON Schema regenerated. **Deviation from the M07 spec:** the spec builds the aggregates/line items as `Expression`s; per user direction these are now `Var` + defining `Constraint` (unit tests stay solver-free by propagating through the constraints via `calculate_variable_from_constraint`).
- **Fuel is costed on a volume basis (m³/hr); flex-pse assumes no heating value.** A combustible fuel is metered and billed on volume, so it is no longer modeled as a kW power draw. New `flexcore.nomenclature.FUEL_USAGE` (`fuel_usage_<fuel_name>`, a volumetric flow in m³/hr — deliberately **not** a `PowerKind`) and new `OpsBlockData.register_fuel_usage(var, fuel_name)`, which records a `FuelUsageRecord` on the new `IORegistry.fuel` list; for a `SimpleGasFlow` stream (whose `flow_vol_phase` is already m³/hr) that var is a `Reference` to the stream's flow. `FlexCosting.cost_process()` pulls every registered flow from the model and builds `aggregate_fuel_usage[t, fuel]` **directly in EECO's m³/hr** (`pyunits.convert` rejects a non-volumetric flow loudly), then bills each fuel via `add_fuel_cost` on its own `opex.fuel_<name>` sub-block. Fuels are **discovered from the model** rather than declared: `FlexCosting.register_fuel`, `fuel_spec`, and the `FuelSpec` dataclass are **removed**, along with `PowerKind.FUEL`, `POWER_FUEL`, `PowerRecord.fuel_name`, the `fuel_name` kwarg on `declare_power`/`register_power`, and the per-fuel `opex.eeco_gas_usage_<name>` normalization Var (the aggregate is already in EECO's units). `report_cost` reads the realized fuel bill off `aggregate_fuel_usage`; a model that burns no fuel builds no gas leg and `opex.fuel_cost` is `0`. **Withdrawn as out of spec:** the earlier same-session design in which a fuel was a `PowerKind.FUEL` kW draw converted to a usage rate by a user-supplied `heating_value` and an optional `fuel_units=therm` basis. It contradicted M07 §"a kW heat duty is NOT the fuel-cost input" and architecture §4 (which lists only `power_electrical`/`power_thermal`), and `fuel_units=therm` silently mis-costed fuel by ~2.83× — EECO always interprets its gas series as m³/hr (`gas_consumption_units`) and applies its own CH4 heating value (`2.83168`) only when a tariff prices gas in therms via the bare `charge` column. Energy-basis conversion is EECO's job, not flex-pse's.
- `flexops.costing.opex` now passes `electric_consumption_units`/`gas_consumption_units` (kW / m³/hr) explicitly into every `eeco.costs.calculate_itemized_cost` call instead of relying on EECO's matching defaults, so an upstream default change surfaces as a loud conversion rather than a silently mis-scaled bill. The `fuel_usage` block-attribute name `add_operating_cost` reads is now the `flexcore.nomenclature.FUEL_USAGE` constant rather than a module-local literal.
- New `examples/pump_tank_load_shifting/` — an interactive marimo notebook stretching the M07 headline pump+tank load-shifting LP from one day to a full month (July 2025, hourly), with pump/tank sizing and the tariff demand charge exposed as sliders. Outside the milestone system and expected to move to a separate examples repo after the API freeze; `examples/` is excluded from ruff/black, and `marimo`/`matplotlib` are added to the `dev` extra.
- **First end-to-end economic result: EECO-backed `FlexCosting`; pump+tank LP shifts load off-peak.** `flexops.costing.FlexCosting` (exported as `fo.FlexCosting`) subclasses IDAES `FlowsheetCostingBlockData` and delegates all tariff operating cost to EECO (decision R4). `cost_process()` aggregates every unit's `power_electrical` into a kW series (pulled from the model, so the block may be constructed before **or** after the units) and organizes cost into two sub-blocks: an **`opex`** block holding all operating cost — `electricity_cost` and `fuel_cost` (both built onto it via the M06 `opex.py` bridge) plus a user-defined `fixed_operating_cost` — re-exposed as `aggregate_operating_cost`; and an **empty `capex`** placeholder (`total_capital_cost == 0`, re-exposed as `aggregate_capital_cost`) that later milestones fill. Capital cost enters the objective **only in design mode** (`set_design_mode()`/`set_operations_mode()` are idempotent single-model toggles; no-ops in v0 with an empty sizing registry). `report_cost(model)` returns a categorized `CostReport` (capital vs. operating, each itemized: electricity, fuel, fixed, dr_revenue) recomputed **post-solve** via EECO's evaluator — never the raw objective (R9, §6); in v0 fuel/dr_revenue/capital are zero placeholders. Demand response stays containers-only (a `dr` placeholder + no-op `_build_dr` hook). `FlexCosting.base_currency` and every operating-/capital-cost expression carry the tariff sheet's currency basis (read from the charge `units` column by the new `flexops.costing.tariff_currency_units`; `$` → `USD`), casting EECO's dimensionless cost expressions to it. The headline component test solves a pump→tank LP under the demo tariff and confirms zero pumping in the peak window. New `docs/how_to/build_a_plant.md` skeleton and `FlexCosting` costing-reference section.
- New `fixed_operating_cost` field on `flexcore.config.CostingConfig` (default `0.0`): the non-tariff fixed operating cost ($ over the horizon — maintenance/labor/chemicals), distinct from the tariff's own fixed charge (which EECO folds into the electricity cost). Exported JSON Schema regenerated.
- `OpsBlock` gains an optional `costing_package=` config: when set, `register_power` forwards the unit's power draw to that `FlexCosting` block (the explicit unit↔costing association). Strictly conditional — costing-less units (M04) are unaffected.
- Wired in the external **EECO** package (`eeco==0.2.1`, already pinned in `pyproject.toml`) as flex-pse's tariff/operating-cost engine, with the whole integration collected in `flexops/costing/opex.py` — the **sole `eeco` import point** in the codebase (decision R12; a `grep` convention, not an import-linter contract). Public API exported from `flexops.costing`: `load_tariff`/`load_dr_program` (resolve a `tariff_source`/`events_source` to an EECO object; wrap load errors as `FlexDataError`), `tariff_csv_to_dict` (EECO `rate_data` CSV **or** pre-loaded DataFrame → the dict `load_tariff` accepts, with optional `write_to=` JSON persistence), the pandas signal helpers `price_series`/`is_peak`/`peak_windows`/`price_gradient` (flex-pse helpers over EECO's `get_charge_dict` charge arrays, for logic/heuristic constraints), the in-objective Pyomo bridges `add_operating_cost`/`add_fuel_cost` returning `OperatingCostHandles` (EECO builds the **convex-relaxed** cost `Expression`s via `costs.calculate_itemized_cost`; the wrapper only renames outputs and asserts the demand charge stayed a linear epigraph — the built model classifies **LP**), the post-optimization evaluators `evaluate_cost`/`evaluate_fuel_cost` (the TRUE de-relaxed bill on a fixed realized numpy array — the user-facing number, R4/R9; `evaluate_cost` reproduces a hand-computed PG&E-B-20-flavored monthly bill to the cent, $14,085.00), and the `DRConfig` demand-response container. **DR is containers-only in v0** (architecture §2.4): `DRConfig` loads a DR file and the internal `_build_dr` hook is a no-op — supplying a DR file never changes the objective. EECO reasons in naive local wall-clock time; tz-aware indices are rejected at the wrapper boundary with `FlexDataError`. New costing reference page (`docs/reference/flexops/costing.rst`) and numpy intersphinx mapping (M06).
- `flexops.costing.add_operating_cost` is now the facility-level umbrella that builds the **whole** in-objective operating cost — electricity **and** gas — onto one opex block, returning a single `OperatingCostHandles` whose `total_operating_cost` is the sum across utilities (EECO namespaces its Pyomo components by utility, so `electric_*`/`gas_*` never collide on one block). It reads the facility consumption from the standard series on the block (`block.power_electrical`, `block.fuel_usage`) when not passed, with `electrical_power=`/`fuel_power=` overrides; a utility whose series is neither passed nor present is omitted, and it raises `FlexConfigError` if neither resolves. The former electric-only `add_operating_cost` is renamed `add_electricity_cost` (still exported) and, with `add_fuel_cost`, remains the single-utility builder. **Deviation from the M06 spec:** the spec names `add_operating_cost` as the electric-only bridge; this session renames that to `add_electricity_cost` and repurposes `add_operating_cost` as the combined electric+gas umbrella, folding facility-level aggregation (nominally M07 FlexCosting territory) into M06 at the user's request. The fuel-consumption block attribute name `fuel_usage` is the `flexcore.nomenclature.FUEL_USAGE` constant — a volumetric gas-usage series in m³/hr, not a `power_thermal` kW duty.
- **`add_gas_cost`/`evaluate_gas_cost` renamed to `add_fuel_cost`/`evaluate_fuel_cost`.** Both now take a `fuel_type` keyword (default `"gas"`, the only utility EECO 0.2.1 exposes) so a future EECO hydrogen utility is a new `fuel_type` value rather than a new function. `add_operating_cost`'s `gas_power` param and the `gas_usage` block-attribute convention are renamed `fuel_power`/`fuel_usage` to match.
- `Pump` gains a `power_relation` config option (`"constant_intensity"`, the default, or `"hydraulic"`): the hydraulic relation adds a `delta_pressure[t]` `Var` tied to the inlet/outlet pressure states by the `pressure_change` equality constraint (`delta_pressure[t] == outlet_state.pressure[t] - inlet_state.pressure[t]`), requiring a `property_package` built with `has_pressure=True`, and excludes `pressure` from the inherited inlet-to-outlet bypass (a pump raises pressure rather than passing it through); both `inlet_state.pressure`/`outlet_state.pressure` are registered as IO inputs (fixed boundary conditions, like dispatch flow). Adds a mutable `efficiency` Var (dimensionless, bounded `[0, 1]`, default 0.7, fixed at build), and builds `power_electrical[t] = delta_pressure[t] * inlet flow / efficiency` in place of the constant-energy-intensity law. Patch to M04's `Pump`, deferred at the time for simplicity.

### Changed

- The tariff JSON records key is now `tariff_data` (was `rate_data`, which collided with EECO's own DataFrame/column-schema term): `load_tariff`, `tariff_csv_to_dict`, and the demo fixture/example tariff files updated accordingly.
- `flexops/costing/opex.py` now sources its rate_data column names, charge-column names, and the `electric`/`gas`/`energy` sentinels from `eeco.costs`' own string constants (`UTILITY`, `TYPE`, `CHARGE_METRIC`, `ELECTRIC`, `ENERGY`, …) instead of hardcoded literals, so an upstream EECO column rename tracks automatically rather than silently breaking tariff validation. Which columns flex-pse *requires* stays flex-pse's choice; only the string values are borrowed. A `unit` test guards that the tuples equal EECO's constants (M06).
- Install pipeline is now conda-only: `uv` is removed and `environment.yml` installs the editable package and its Python dependencies (including the pip-only `eeco`) through a `pip:` subsection, so `conda env create -f environment.yml` is the single install command. README, `PLAN.md`, and the M00 milestone spec updated accordingly.
- **Renamed the intra-unit property-copying API to `pass_through`, reserving `bypass` for the flow-diversion stream.** `OpsBlockData.add_bypass_constraints` → `add_pass_through_constraints`, the config slot `allow_bypass` → `allow_pass_through`, and the generated equality components `bypass_{name}_eq` → `pass_through_{name}_eq`. This copies every state variable a unit does not otherwise govern straight through (`outlet == inlet`) so a single unit is well-posed — distinct from a *physical bypass* that diverts flow around a unit (`flexops.logic.bypass.add_bypass`, which keeps the `bypass` name). Behavior-preserving: no constraint math changed. **Deviation from the M04 spec**, which named the method `add_bypass_constraints`/config `allow_bypass`; the M04/M03 milestone wording is updated to match, and a new `docs/explanation/pass_through_and_bypass.md` page distinguishes pass-through (intra-unit, now) from the bypass stream (flow diversion, M08) and the arc/topology layer (M09).

### Added

- Project scaffold: four-package `src/` layout (`flexcore`, `flexops`, `flexparameterize`, `flexschedule`), import-linter DAG contract, pytest tier markers with collection-time enforcement, and CI skeleton (M00).
- Exception hierarchy; pinned idaes-pse/pyomo versions (M01).
- Added `TimeBlock`: the discrete-time substrate (ordered integer `time_index` set, `time` Param of elapsed `i*dt` in the user's units, unit-carrying `dt`, datetime↔index utilities, rolling-horizon initial-state registry and window metadata); a configurable `max_length` (dateutil `relativedelta`, default one calendar month) bounding the horizon; minimal Sphinx docs skeleton (M02).
- CI `standard-install` job (committed but commented out, pending the repo going public): remote-only install from the git ref (`pip install "git+<repo>@<ref>"`, no checkout) matrixed over Python 3.11–3.14 that imports every subpackage from a scratch dir, catching subpackages missing from the built distribution — or files left uncommitted — that the editable dev install would mask (M00).
- Added `flexcore.solvers`: a model classifier (`classify`/`ProblemClass`), a capability-matrix registry with cached availability probing (`available_solvers`), and the `get_solver`/`SolverFacade` facade that selects a solver by problem class and errors loudly (decision R5) when no capable solver is installed. Default open-source stack: HiGHS for LP, **SCIP for MILP and MINLP** (preferred over HiGHS for MILP; added to `environment.yml`), and IPOPT for NLP — built from idaes (HSL `ma27` linear solver) when idaes is importable, falling back to stock `SolverFactory` IPOPT (MUMPS) otherwise. When no MINLP-capable solver is installed, MINLP still raises pointing at `flexschedule.SolveSequence`. SCIP's dynamic-library path is isolated at invocation so it does not clash with idaes's bundled `libipopt`. The root `conftest.py` now forbids solver invocation and network access under `-m unit` and skips `needs_*`-marked tests via the registry; adds a `flexcore` reference page and a relaxation-policies explanation page (M05).
- Added the `OpsBlock` base of every flex-pse unit model (`flexops.core.ops_block`, inheriting IDAES `UnitModelBlockData` with no ControlVolumes, decision R1): the registration API (`register_io_variable`/`register_process_parameter`/`register_power`), base-provided `power_electrical`/`power_thermal` kW Vars via `declare_power`, the external-dispatch (DERMS) hook `set_external_dispatch`, the validated-only config slots (`unit_commitment`, `relaxation`, `allow_pass_through`, `external_dispatch`; their constraints land in M08), and an M09-deferred `build_from_config` stub. `register_power`/`declare_power` require a `flexcore.nomenclature.PowerKind` member for `kind` (plain strings are rejected), and call sites import the nomenclature module as `nm` so constants like `nm.POWER_ELECTRICAL` read unambiguously as string names. Added the in-place update hook `update_parameters(values)` (`set_value` on registered mutable params, driven by FlexParameterize in M10): flex-pse never deletes model components — deletion leaves stale references in anything that captured the old component — so the earlier delete-and-rewire `replace_unit` helper was dropped in favor of it (conventions §9). Registration records and model-wide discovery live in `flexops.core.registration` (`IORegistry`, `iter_io_registry`). Added the `add_stream_ports` helper: it builds a single scalar inlet/outlet state block per stream from the configured `property_package` (state variables indexed over time), registers each side's volumetric flow (`flow_vol_phase`) as an input/output IO variable via a time-indexed `Reference`, and exposes the `inlet`/`outlet` ports through the inherited IDAES `add_inlet_port`/`add_outlet_port` (M03).
- New `model_and_block_structure` explanation page: defines the ConcreteModel/`TimeBlock`/`OpsBlock`/property-package block hierarchy and the variable-indexing convention (operational Vars indexed over `time_index`; property state variables carry the time index themselves on a single scalar state block per stream), plus the extensive/intensive arc split.
- Added `SimpleAqueousFlow`: the minimal IDAES property package whose state block carries a `flow_vol_phase` indexed by time then phase (single `Liq`), and a time-indexed `dens_mass` state variable (fixed at the configured `density` by default, free with `fixed_density=False`), plus opt-in `pressure`/`temperature`. State variables are indexed over time directly — extensive per-phase quantities lead with time then phase, intensive stream properties (`dens_mass`/`pressure`/`temperature`) drop the phase index — and the owning unit passes the time set via a `time_index` state-block config option, yielding one scalar state block per stream; exported from `flexops` (M03).
- Added `SimpleGasFlow`: the gas-phase counterpart of `SimpleAqueousFlow` whose state block always carries a `flow_vol_phase` (indexed by time then the single `Vap` phase), plus time-indexed `dens_mass`, `pressure`, and `temperature` (gas density varies with pressure/temperature; no equation of state is imposed). Exported from `flexops`, alongside a new top-level `PowerKind` re-export so the standardized power-kind names (`PowerKind.ELECTRICAL`/`PowerKind.THERMAL`) are importable directly from `flexops` (M03).
- Added the full versioned config schema (`flexcore.config.schema`, pydantic v2, decision R3): `IOVariableSpec`, `SurrogateSpec`, `ExternalDispatchSpec`, `UnitCommitmentConfig`, `UnitConfig`, `PlantConfig`, `NetworkConfig`, `TimeConfig`, `CostingConfig` (with a `DRConfig` container slot), and the top-level `ModelConfig` (mandatory semantic-version `schema_version`, exactly-one-of `network`/`plant`). Added `flexcore.config.io` (`load_model_config`/`dump_model_config` with JSON as the only on-disk format plus direct dict input, a `MIGRATIONS` table, and `export_json_schemas` with an optional `filename` for side-by-side schema versions) and the checked-in JSON Schema at `src/flexcore/config/schemas/model_config.schema.json`, whose descriptions are exported as plain single-line text (no newlines or section-sign codes; wrapping is the doc builder's job). Added `flexcore.nomenclature` (the `POWER_ELECTRICAL`/`POWER_THERMAL` constants and `PowerKind`). New docs: config-schema and energy-nomenclature explanation pages, `flexcore` config/nomenclature/exceptions reference sections, and a `flexops.properties` reference page (M03).

- Added the public, shipped `flexops.testing.UnitModelTestHarness`: every unit-model milestone (and any user writing a custom unit model) subclasses it instead of hand-writing the build/units-consistency/registration/energy-naming/degrees-of-freedom/solve/solution checks (`test_build`, `test_units_consistent`, `test_io_registration`, `test_energy_naming`, `test_dof` on the `unit` tier; `test_solve`, `test_solution` on the `component` tier, skipping cleanly if `flexcore.solvers.get_solver` is unavailable). Added `flexops.testing.dummy_time_block(n=3)`, a throwaway `TimeBlock` + `SimpleAqueousFlow` model reused by the M14 docs generator. Added `OpsBlockData.add_pass_through_constraints(inlet, outlet, *, exclude_vars=())`: a generic inlet-to-outlet pass-through for every non-excluded, non-fixed state variable (e.g. `dens_mass` under `fixed_density` is skipped automatically), gated by `self.config.allow_pass_through`; it resolves each port's sibling `"{port}_state"` block rather than the port's own `vars` mapping, since the latter are auto-generated `Reference`s carrying a leaky extra `UnindexedComponent_set` dimension. Added `SISOBlock` (`flexops.unit_models.base`), the first IO-topology base class (architecture §3.4/R6): builds the inlet/outlet ports via the inherited `add_stream_ports`, then its per-stream pass-through via `add_pass_through_constraints` with no exclusions (flow's pass-through is itself a pass-through equality, named `pass_through_flow_vol_phase_eq`); `SISOBlock` overrides the inherited `allow_pass_through` default to `True` so the topology is well-posed out of the box. Added `SimpleAqueousFlow.get_flow_basis_var_name()`/`SimpleGasFlow.get_flow_basis_var_name()` (both return `"flow_vol_phase"`), letting callers exclude "the flow" from a generic pass-through without hardcoding a property-package-specific name. Added the first two physical unit models on top of the SISO base: `Pump(SISOBlock)` (`power_electrical[t] = energy_intensity * inlet flow`, dimensionally exact kWh/m³ × m³/hr = kW; carries a `.. todo::` note for a future detailed power law, e.g. density·flowrate·head/efficiency, not built here) and `Tank(SISOBlock)` (holdup difference equation `volume[t+1] = volume[t] + dt*(in - out)` over `t = 0..N-2`, converting the whole flow-difference expression rather than assuming the flow basis's units). `Tank` now distinguishes `max_volume` (the maximum *possible* tank volume -- fixed by prior investment or space constraints, a static upper bound) from `capacity` (the *chosen* volume, a fixable design `Var` now bounded `(min_volume, max_volume)` so a design-mode solve can never exceed the maximum possible size). Added a bounded `level[t]` Var (`level_min`/`level_max` config, default `(0.0, 1.0)`) defined by `level_definition[t]: volume[t] == level[t] * capacity` -- the fractional fill relative to the *chosen* capacity, preventing the tank from draining all the way down or overfilling; this is linear (LP) in operations mode (`capacity` fixed) but bilinear (**NLP**) in design mode (`capacity` free), so design-mode solves of a model containing a tank need IPOPT or a `flexschedule.SolveSequence`, not HiGHS. `Tank` forces `unit_commitment.status = False` regardless of what a caller passes -- a tank has no on/off status, the canonical example of a physical subclass turning off a base capability (R6).
